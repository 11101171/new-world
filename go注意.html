1为什么 Go 同时有 var 和 :=

问：为什么 Go 会有这两种变量声明方式？

var 是显式声明：包级别只能用它（顶层语句必须以关键字开头，便于编译器快速解析），且能表达"零值"和显式类型。:= 是短变量声明，只能用在函数内部，为高频的局部变量场景而生，配合多返回值的错误处理惯用法（v, err := f()）尤其方便。

设计哲学：让常见情况简短，让特殊情况显式。实践惯例——函数内默认用 :=，需要零值/显式类型/包级别时用 var。

代价：:= 的"至少一个新变量"规则容易造成变量遮蔽（shadowing），是常见 bug 来源。

语法设计变量声明

2panic / fatal / recover 不是"三种错误"

问：Go 为什么要设置这三种"错误"？

纠正概念：这三者不是错误类型，Go 真正的错误只有 error 接口。

性质用途
error接口可预期的失败，调用者显式处理
panic内置函数不可恢复的程序 bug，沿调用栈展开并执行 defer
recover内置函数只能在 defer 中调用，截住 panic，防止服务崩溃
fatal非内置，log.Fatal / 运行时 fatal error无法继续运行，不能 recover，直接 os.Exit
经验法则：能预见的失败用 error；代码 bug 用 panic；服务边界防崩溃用 recover；main 启动失败用 log.Fatal。
错误处理

3指针接收者 vs 值接收者

问：为什么函数命名有指针和非指针两种方式？

本质是方法的接收者（receiver）。Go 参数传递永远是值拷贝：值接收者操作副本，指针接收者操作原对象地址。

  • 需要修改接收者、结构体很大、含不可拷贝字段（如 Mutex）→ 用指针
  • 小型不可变值（如 time.Time）→ 用值
  • 同一类型的方法风格要统一
方法集规则：T 的方法集只含值接收者方法；*T 的方法集含全部。这决定了谁能实现接口——var _ Incer = Counter{} 若 Inc 是指针方法会编译错误。
方法接口

4为什么需要 GMP 调度模型

问：GMP 模式有什么优势？

G=Goroutine（用户态协程），M=系统线程，P=逻辑处理器（持有本地队列和分配缓存）。M 必须绑定 P 才能执行 G，实现 M:N 调度。

早期 GM 模型只有全局队列，锁竞争严重；引入 P 后把资源和队列下放到 P 上：

  • 本地队列大多数调度无需加锁
  • 工作窃取（work stealing）实现负载均衡
  • 系统调用阻塞时 P 可被摘走交给别的 M（hand off），不浪费资源
  • netpoller 让网络 I/O 不占用线程，支持同步写法获得异步性能
  • 基于信号的异步抢占，防止死循环饿死其他 G

5内存分配借鉴 TCMalloc 的多级缓存

问：为什么要借鉴这种思想？

目标同样是避免多核下全局堆分配的锁竞争。核心思想：按对象大小分级（size class）+ 线程本地缓存 + 多级结构。

层级结构特点
一级mcache每个 P 一个，分配无锁
二级mcentral按 size class 共享，需加锁
三级mheap全局堆，向 OS 申请内存

mcache 挂在 P 上而非 M 上，因为 P 数量固定可控，M 会因系统调用频繁增减。Go 与 TCMalloc 的差异在于：Go 有 GC，span 记录 bitmap 配合标记清扫，不需要主动搬运缓存对象。

6逃逸分析：为什么会逃逸到堆

问（配图表格）：返回局部变量指针、赋值给 interface、闭包捕获、大小未知、存入堆/全局/channel，为什么会逃逸？

核心原理：编译器判断变量生命周期是否可能超过创建它的函数。可能超过，或无法证明不会超过 → 放堆上。
  • 返回局部变量指针：函数返回后栈帧回收，但调用者还持有地址，必须放堆
  • 赋值给 interface：接口内部存指针，编译器无法确定是否被长期持有或反射使用，保守放堆
  • 闭包捕获：闭包被返回后仍存活，捕获的变量必须跟着活下去
  • 大小未知/过大：栈帧大小必须编译期确定，变量大小放不进栈
  • 存入堆对象/全局变量/channel：被更长寿的容器引用，自己也必须更长寿

查看方式：go build -gcflags="-m" main.go

7为什么 Go 也有堆和栈

问：堆和栈各自解决什么问题？

栈快但只能存活到函数返回；堆灵活但分配/回收有代价。Go 的特别之处：程序员不显式选择，编译器通过逃逸分析自动决定能放栈就放栈。

goroutine 栈初始仅约 2KB，可动态扩容（搬迁并修正指针），用不完会收缩——这也是栈上变量地址不能被堆对象长期持有的原因之一。

8并发标记与写屏障

问：标记与用户代码并发执行，用户代码修改指针为什么会破坏正确性？

三色标记：白（未访问，最终回收）、灰（已发现待扫描）、黑（已扫描完）。漏标需同时满足两个条件：

  1. 黑对象新增了对白对象的引用
  2. 所有从灰对象到该白对象的路径被断开

满足即导致存活对象被误回收（比内存泄漏更严重的悬空指针）。

解决方案：写屏障。Go 1.8+ 使用混合写屏障（删除屏障 + 栈灰色时的插入屏障），既维持三色不变式，又避免重新扫描栈，把 STW 压到微秒级，代价是少量"浮动垃圾"。

9map 是拉链式哈希表

问：如何理解？

Go 1.23 及以前：每个桶（bucket）存 8 个 kv，存不下挂溢出桶形成链。桶内存 tophash（哈希高 8 位）加速比较，key/value 分开连续存放减少内存对齐浪费。扩容分负载因子超限（翻倍扩容）和溢出桶过多（等量扩容），且是渐进式迁移。

Go 1.24 起默认改为 Swiss Table（开放寻址 + 分组控制字 + SIMD 加速），语义不变（无序、非并发安全、不可取地址），性能更优。
map哈希表

10map 非并发安全

问：如何更好地理解？

一次 m[k]=v 实际由多步组成（算 hash、找槽位、写入、计数、可能扩容），多 goroutine 交错执行会破坏内部结构。Go 用 flags 标记位尽力检测，发现并发读写直接触发 fatal error（不可 recover），而不是让程序带着损坏数据继续跑。

规则：只读并发安全；只要有写就必须同步。常用方案：sync.RWMutex（最常用）、sync.Map（key 写一次读多/互不相交场景）、分片锁、channel 串行化。测试务必加 -race。
map并发安全

11无缓冲 channel 为什么阻塞

问：为什么无缓冲 channel 会阻塞？

无缓冲 channel 容量为 0，没有地方存数据，发送的值只能直接交到接收方手上——即 rendezvous（会合）语义：发送和接收必须同时发生。

价值所在：无缓冲 channel 保证"发送成功"等价于"接收方已经拿到数据"，这是 CSP 模型"用通信实现同步"的基础，常用于 done-channel 这类完成通知。
操作无缓冲有缓冲
发送阻塞直到有接收者缓冲区满才阻塞
接收阻塞直到有发送者缓冲区空才阻塞

12happens-before

问：如何理解 Go 的 happens-before？

回答"一个 goroutine 写的值，另一个 goroutine 什么时候能保证看到"。没有同步原语，普通变量的跨 goroutine 可见性和顺序都不保证（编译器重排+多核缓存）。

建立 happens-before 的方式：channel 收发（发送 hb 对应接收完成）、Mutex 的 Unlock hb 下一次 Lock、WaitGroup 的 Done hb Wait 返回、Once.Do(f) hb 任意一次 Do 返回、atomic 写 hb 读到该值的读、go 语句 hb 新 goroutine 开始执行。

口诀：没有同步，就没有顺序，也没有可见性。 没有 happens-before 路径即为数据竞争，用 -race 检测。

内存模型并发

场景方案依据

14公用 Service 应该用哪种方式加载

问：Web 里公用 service 类应该怎么加载？

  • 首选：依赖注入 + 启动时构造，构造完只读，天然无锁（main hb 每个请求 goroutine）
  • 需要热更新的单个字段 → 单独用 atomic 包裹，不要给整个 service 加锁
  • 内部有可变共享状态（如内存缓存）→ 只给该字段加 RWMutex，不要锁整个结构体
  • 初始化时机不确定、只需一次 → sync.Once
反模式：包级全局变量 + 手写懒加载判空（数据竞争）；service 里塞 *http.Request 等请求作用域数据（并发请求会互相污染）；用全局裸变量代替依赖注入（难测试）。

15Worker Pool：range vs select，以及死锁

问1：为什么用 for range 而不是 select？
问2：为什么 wg.Wait() 不能直接写，会和 worker 互相等待？

① 只处理单个 channel、且想等到它关闭为止 → range 足够清晰；需要同时监听多个 channel 或支持取消 → 才用 select。

② 若 wg.Wait() 直接写在 main 里（不开独立 goroutine），main 会卡在 Wait 上，此时没有人在消费 results。若任务数超过 results 缓冲区容量，worker 会阻塞在 results<- 上等人来取，而 main 在等 worker 全部 Done —— 互相等待，死锁。

正确做法：把 wg.Wait()+close(results) 放进独立 goroutine，让它与 main 的 range results 并发执行——"消费腾空间"和"等待后关闭"必须并发而非串行。

16单向 channel（chan<- / <-chan）

问：如何理解 chan<- int 是单向的？

不是新类型，而是对同一个 channel 的受限视图，底层指向同一个 hchan，运行时无额外开销。箭头指向谁，数据就往谁那边走。

作用：用函数签名表达契约（一看就知道只读还是只写），编译期拒绝误用；只有持有可写权限的一方才能 close，防止接收方误关闭 channel。双向可隐式转单向，但单向不能转回双向（权限只能收紧不能放宽）。

17闭包捕获循环变量的写法

问：go func(c <-chan int) { ... }(c) 是什么写法？

匿名函数 + 立即调用（类似 IIFE），并通过参数值拷贝把循环当前的 c 绑定为新 goroutine 内部独立的局部变量，避免多个 goroutine 共享同一个外层循环变量。

Go 1.22 之前，for range 的循环变量是同一个变量被反复赋值，闭包直接捕获会导致所有 goroutine 读到同一个值（通常是最后一个）；Go 1.22+ 已修复语义，但显式传参仍是更清晰、不依赖版本的惯用写法。

18Pipeline 中 channel 的关闭传播

问：in 没有被显式 close，square 里的 goroutine 不是会一直运行吗？

in 由 gen 内部创建并负责 close（defer close(out)），遵循"谁创建 channel 谁负责关闭"的原则，调用方不需要也不应该去关。

关闭是一条连锁反应：gen 发完数据 close(in) → square 的 range 退出并 close 自己的输出 → merge 的搬运 goroutine 退出，wg.Done() → merge 的等待 goroutine 收到后 close(out) → 最外层 range 退出。每一层只管好自己的输入/输出。

19context.cancel 的本质

问：cancel() 为什么没有发现有这个函数？

cancel 不是包级函数，而是 context.WithCancel(parent) 返回的第二个值——一个闭包（CancelFunc），捕获了对应的 ctx，调用它会关闭 ctx 内部的 Done channel。

职责分离：ctx（只读）交给被控制方监听是否该退出；cancel（能触发关闭）留给控制方决定何时喊停。调用了 WithCancel 就应保证 cancel 最终被调用（通常 defer cancel()），否则有轻微资源泄漏风险。

20select + time.After 验证 goroutine 正确退出

问：这段 select 会执行到哪个分支？

会走 <-finished 分支。cancel() 触发 ctx.Done() 关闭 → producer 的 select 立刻感知并 return → defer close(finished) 触发 → finished 关闭使 <-finished 立刻就绪，整个过程远快于 1 秒。

time.After(1s) 只是超时兜底：仅当 producer 没有正确响应取消、永不退出时才会触发"泄漏了"分支。这是验证 goroutine 是否正确退出的常见测试套路。

21channel 什么时候不需要 close

问：为什么 out 没有 close？

main 消费 out 用的是固定次数的 <-out，不是 range out，所以不依赖"channel 关闭"作为退出信号。取消是异步发生的，发送方无法保证关闭时自己绝对不在发送中途，贸然 close 会给未来的改动埋下"向已关闭 channel 发送导致 panic"的隐患。

判断标准：消费方用 range 等待结束 → 发送方必须 close；消费方自己知道该收几个、何时不再收 → 不需要 close。另外，channel 本身可被 GC 回收，不像文件/连接那样必须显式关闭才能释放资源，close 只是一种"通知信号"。
